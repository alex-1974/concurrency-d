# R0.5 — Victim search sequence recurrence: source/model/native trace audit (2026-10-13)

**Research decision: KEEP complete foreign-victim coverage; DO NOT promote first-victim rotation, reduced foreign-probe count, cached-empty hints or another worker search mechanism based on these traces.** The current R0.5 full N-candidate-position search visits every foreign worker deque **exactly once within each fully unsuccessful scan**, but its `nextVictim` cursor returns to the *same* starting position after a complete failure. Native worker-local traces independently confirm unchanged scan order between failure cycles **without intervening work acquisitions**. This is an **ordering/repeated-access observation**, not evidence that the later checks can safely be skipped or that avoiding them yields net CPU/throughput savings. The already-tested rotating-first-victim alternative did **not** deliver a stable native speed or wake-tail benefit.

## Source and provenance

- Code audited: `source/concurrency/internal/submission_pool.d`, `workerLoop(size_t self)`, on the grandfathered `perf/r05-owned-task-pipeline` branch. The active FullVictimSweep research version iterates `_queues.length` **candidate positions**, increments `nextVictim` modulo worker count on each, skips `victim == self`, and tries at most **N−1 distinct foreign deques** per fully missed sweep. On an unsuccessful scan this naturally returns `nextVictim` to its previous start. The `R05RotatingFullVictimSweep` branch explicitly adds another cursor advance, skipping `self` if necessary; it is distinct compile-time research code.
- Original trace evidence: user-provided, unchanged **`r05-xps-victim-sweep.tar.gz`**, pinned SHA-256 **`46653953b304ff5567f8656a693acb30e4bc11ba993afa22358e7b43172cc111`**, measured **Git SHA `882de033136617311e7b08ac20d84862a3b7a015`**, native XPS i7-9750H, LDC 1.41.0/LLVM 19.1.7. Contains **4,110 worker-local search events**, grouped into **320 per-worker/case streams** for `old` and `full` across four workers, five rounds and GC/recycle × always/waiter × three/four blocker cases. The raw data were **not** committed to Git; the original archive remains the authoritative evidence.

Source report CSV: [xps-victim-repeat-trace-audit-2026-10-13.csv](xps-victim-repeat-trace-audit-2026-10-13.csv).

## Exact within-worker replay (4 workers)

A **fully unsuccessful scan** here means a per-worker consecutive sequence of foreign `stealMiss` events ending at `searchEmpty`; no thief obtained a Task in that particular search. For the four-worker trace, the full-sweep must contain precisely **3 unique non-self victims**; old `N−1`-candidate scans contain **2 or 3**, depending on whether the self position consumed one candidate.

| Audit criterion | Old N−1 candidate positions | Full N candidate positions |
|---|---:|---:|
| Native fully empty search scans | **278** | **271** |
| Scans omitting at least one foreign victim | **211** | **0** |
| Successive recorded empty-scan pairs, same worker | **118** | **111** |
| Of those: intervening work acquired before second failure | **16** | **11** |
| **Pairs with no intervening work acquisition** | **102** | **100** |
| Same full foreign victim order in those pairs | **0/102** | **100/100** |
| Different foreign victim order in those pairs | **102/102** | **0/100** |

These counts were independently recomputed from `worker_search_events.csv`, not reconstructed by dividing aggregated Task counters. For every fully empty scan, no repeated foreign queue index appears **within** the scan. The old scan's changed repeated-cycle ordering arises naturally from consuming only N−1 candidate positions, but **211/278 old failed scans did not cover all foreign workers**. That old apparent scan rotation is *not* a safe substitute for complete victim coverage.

The `100/100` observation proves only **same-index victim sequence on successive failure scans with no intervening successfully acquired Task** in this fixed configuration. It does **not** establish that any deque was continuously empty, that its contents did not change between individual probes, that a notification was unnecessary, or that the repeated deque operation consumed a known number of CPU cycles. Event timestamps are worker-local and logged after each action; they are **not a globally serialized queue history**. Intrusive worker-local trace capture is not the uninstrumented throughput control.

## Critically, rotating search has already been implemented and tested

The existing `R05RotatingFullVictimSweep` research variant was subject to the full [native long mixed/idle/burst A/B](xps-rotating-victim-review-2026-10-11.md), measured on source **`3c8a5031ca437794afac77220b7b1adfc8584d40`** under matched batch8 / LDC1.41 and 100k mixed Tasks per child. The earlier report's original XPS archive is pinned SHA-256 **`7a58705a85854104c6e1af6161e505e525c65f392dcbe4c30ec42acdf12fe7e6`** and remains unchanged.

**Independently rechecked against that original archive's `r05-xps-rotating-controls/pairs.csv`:** among **80** within-round `rotating/old` mixed-throughput ratios (four workers, both policies, both notify modes, 1/4 producers, minimal/compute; five rounds), descriptive median **0.97019×**, rotation faster in only **31/80**. Do not claim equivalence or guaranteed regression from this small/noisy suite, but clearly **no stable benefit**. The native report also found that the paired four-worker `gc/always` rotating wake p99 exceeded the simpler complete sweep in **9/10** comparisons, median ~**+65.8µs**; with only 64 wake samples/run, nearest-rank p99 is literally one maximal response. This is a **cautionary adverse tail signal**, not a qualified production p99 regression.

**Important baseline distinction:** In the 80-pair control statistic above, `old` is the incomplete N−1 victim-position search, not the **full** corrected sweep. Direct rotating/**full** comparisons in the same original native report also lack a stable benefit. One cannot use relative 0.970× against old as an isolated rotation-versus-full causal estimate, nor pool its different codegen into this later source revision. The simpler complete foreign-victim coverage (already separately accepted through the narrow production M0 coverage fix, PR #37) remains the correctness baseline.

## Decision and next meaningful research

1. **CONFIRMED:** full-sweep code makes no redundant victim deque probe within a completed search. Consecutive fully failed scans can revisit the same victim order, even if a worker genuinely parked between them. The candidate-position model establishes this for all audited worker counts (not just N=4).
2. **ALREADY TESTED / DEFERRED:** changing only the starting victim via `R05RotatingFullVictimSweep` preserves full coverage but has no reliable performance or idle wake benefit. Do **not** launch the same rotation A/B again or quietly select it as default.
3. **NOT QUALIFIED:** memoizing that a victim deque was empty, skipping foreign victim probes, reducing to the old N−1 candidate positions, inserting backoff/spinning or suppressing notifications. A thief's empty observation is transient under concurrent publication; the inbox wake-generation ticket guards park/wake progress, not arbitrary per-queue empty-cache correctness. Any truly safe hint would need additional publication visibility and memory-model proof, and can itself create atomics/cache traffic. None is supported by current native net-performance evidence.
4. **NEXT:** before spending another XPS campaign or implementing another scheduler candidate, distinguish **actual deque operations versus the larger producer admission/worker parking costs** with a mechanism-specific model or genuinely new source evidence, including fully blocked-worker progress and idle wake-tail correctness. Candidate work should be a separately scoped research issue with explicit semantic equivalence and acceptance metrics; do not fold an unbounded redesign into Draft PR #35.

No changes to `freshGc`, `NotificationPolicy.always`, worker/deque/TaskRef ownership, retention/admission limits, generation-safe condition wait, full foreign-victim scan, public API, or other workspace repositories. Draft PR #35 stays open and Draft; Issue #20 stays open; **no broad research merge into `develop`**.
