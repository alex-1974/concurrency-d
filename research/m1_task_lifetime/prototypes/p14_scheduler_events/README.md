## Question

P13 supplied a **summary-only** three-session XPS result: 4-worker/2-worker duration ratios fall from 1.676× for zero-iteration tasks to 0.899× for 512 iterations; a small ingress of 8 is expensive for tiny tasks, and its `parkCount` and producer retries rise. Those observations justify investigating **which M0 scheduler paths are exercised**, **not guessing** that one lock/steal/park operation causes the effect.

The unchanged M0 [`source/concurrency/internal/submission_pool.d`](../../../../source/concurrency/internal/submission_pool.d) uses:

- a **shared mutex** for every `trySubmit` and `completeOne` (at least two global critical-section visits for every successfully completed task);
- per-TaskRef notification after accepted submissions and generation-based park/wake protection;
- **ingress batch capacity 8**, with extra items placed on the owner-local deque;
- **single-item cross-worker steals**, not batch stealing;
- a worker loop that first checks owner-local deque, then ingress, then victim queues and finally parking.

These are source-derived architectural properties, **not measured costs**. P14 counts these transitions without touching `source/`.

## The two actually compared binaries

No runtime instrumentation branches are inserted into production M0. The overlay is generated by [`m1_p14_make_instrumented_pool.py`](../../../../tools/research/m1_p14_make_instrumented_pool.py), which checks that the source's Git blob SHA is exactly **`b7d8fafcb3179f00cba7e89e28c6d6b9b676353a`** and rejects changed source instead of silently applying assumptions. Its one-time insertions are guarded by exact source anchors. The cloned module is renamed to `concurrency.research.m1_p14_pool`; production scheduler queues, wake predicates, atomic semantics, batch order, and worker behavior are otherwise unchanged.

The generated P14 workload and CSV driver come from a **separately pinned** copy of P13 via [`m1_p14_make_fixture.py`](../../../../tools/research/m1_p14_make_fixture.py). It requires P13 kernel Git blob `3852e8788757b62c5000ad55565359d6a20a78c1` and P13 driver Git blob `723de6bf76ac838b10de4b3f1cb901315a5ced38`. Both copies contain the same P13 TaskRefs, deterministic integer work, wave boundaries, no record reuse/free before native join and independent result oracle. The tracing copy simply adds an after-join `p14Snapshot()` and columns for event counts.

**Generated sources are build artifacts, not a source of truth, and are not committed.** If M0 or P13 changes, the runner intentionally fails until somebody audits and updates the pinned generator.

## Precisely counted scheduler events

| Counter family | Meaning and limitation |
|---|---|
| `accepted_submits`, `full_submits` | Accepted and full `trySubmit` outcomes, under the **existing inbox mutex**; full submissions must equal the producer's retry count. |
| `submit_signals` | `notify` calls from successful submissions (not actual awakened threads). |
| `local_signals` | `notify` calls when a worker publishes work on its local deque. |
| `complete_calls`, `final_signals`, `close_signals` | Completion accounting and notifications on drain/close; these count *invocations*, not mutex wait duration. |
| `batch_attempts`, `batch_claims`, `batch_tasks` | Inbox takeBatch calls, nonempty returned batches, and number of records acquired from the inbox. Mean nonempty batch occupancy can be derived as `batch_tasks / batch_claims`. |
| `local_pushes`, `local_push_failures` | Success/failure to place the rest of a claimed batch on the owner deque. A failed push executes inline under the original M0 policy. |
| `local_hits`, `local_misses` | Successful and empty local-owner `pop` operations. |
| `steal_attempts`, `steal_successes` | Calls to an actual other-worker deque's `steal()`, and successful returned TaskRefs. These do **not** count stolen batches: M0 presently steals one TaskRef per call. |
| `park_attempts`, `park_waits` | Calls to the generation-guarded `parkUnlessChanged` and existing `TaskInbox._parkCount` increments before `Condition.wait`; neither records actual blocked time. |
| `executed`, `worker_count`, `worker0_executed` … `worker15_executed` | Tasks executed in the actual workerLoop, with cache-line-aligned, **single-writer per-worker counters** read after joining all native workers. Unused worker columns are zero. |

The per-worker buffer is `align(64)`; only the owning worker writes its own counters. Inbox counters increment while the *existing* mutex is held. There are no new cross-worker atomic counters in the task hot path, no per-task log allocations or per-event clock calls. **However, instrumentation still changes instruction count, cache placement, shared critical-section duration, and the pool's allocations**; even an aligned research stats array can perturb cache behavior. The trace/control timing ratio is therefore an **instrumentation overhead diagnostic**, not a correction factor to subtract from an uninstrumented performance result.

### Explicit conservation gates

Before emitting any trace row, the runtime checks all of these with exceptions that remain active in LDC release mode:

```text
accepted_submits = submit_signals = complete_calls = executed = batch_tasks
                 = count × waves
full_submits     = producer_retries
park_waits       = original_M0_parkCount
batch_tasks      = local_pushes + local_push_failures + batch_claims
local_pushes     = local_hits + steal_successes
executed         = local_hits + steal_successes
                 + batch_claims + local_push_failures
steal_successes <= steal_attempts
sum(worker[i].executed, i < worker_count) = count × waves
```

The [P14 CSV checker](../../../../tools/research/m1_p14_compare.py) independently requires matching `phase/round/order/seed/workers/count/waves/iterations/ingress/checksum` on **every row** of control versus trace. Control must emit **zero trace events**; trace must pass all conservation checks and retain zero counts for nonexistent workers. It also prints per-configuration **minimum and maximum worker execution counts**, but does not turn 2–3 shared-CI samples into a load-balancing theorem.

If any identity fails, the qualification **FAILS**, regardless of how plausible the timings look.

**Integrity:** LDC 1.41.0 release, Intel Core i7-9750H, process affinity CPUs 0–3 mapping to **four distinct physical cores** in the saved CPU topology. Three sessions × 45 configurations × (two warm-ups + seven measured sweeps) for **both** unchanged M0 and event-instrumented M0 gives 2,430 total rows and 1,890 measured rows (945 per mode). All task-result checksums, matching seeds/configuration order, complete 45-case sweeps, per-worker execution totals, event conservation and time-segment sums were verified.

**UNINSTRUMENTED control within-sweep 4-worker/2-worker median `waves_ns` ratios**: **1.788× / 1.643× / 1.483× / 1.195× / 0.931×** for task kernels **0 / 8 / 32 / 128 / 512 iterations**, respectively; each median uses **63** within-sweep, same-work comparisons across three sessions and three ingress settings. Four workers were faster in **0 / 1 / 0 / 9 / 46** of those 63 comparisons. This independently confirms P13's task-granularity crossover in active multi-wave pools without asserting a general worker-count optimum.

**TRACE path data**, 6,144 zero-iteration jobs and 4 workers, median of 21 samples per ingress:

| Event | Ingress 8 | Ingress 64 | Ingress 256 |
|---|---:|---:|---:|
| Steal attempts | 4,785 | 1,189 | 1,012 |
| Successful steals | 850 | 288 | 236 |
| Actual park waits | 642 | 145 | 123 |
| Producer full-ingress retries | 877 | 34 | 1 |
| Mean tasks/nonempty ingress batch | 4.2 | 6.4 | 6.5 |

Every configured worker executed some of the 6,144 tasks in **every one of the 945 traced measured configurations**. The short-task four-worker slowdown is thus not simply caused by idle workers receiving no tasks. One-worker/zero-iteration/ingress-8 workloads still incurred around **404 waits and 1,239 retries** with **zero stealing**, strengthening the case to investigate ingress/backpressure/parking separately from thief scheduling.

**Instrumentation perturbation:** the median trace/control ratios across sessions were **0.973 / 1.030 / 0.914**, with process ordering alternated. The trace sometimes measures *faster* than control due to uncontrolled timing variability, so we reject any claimed calibrated overhead or subtraction. Native temperature snapshots were around 76–81°C but not continuous frequency/thermal traces. The source analysis distinguishes real-control scaling from traced event counts.

**Disposition:** KEEP the P14 counters and completed native evidence. **DEFER** modifications to production M0, batching/wake/steal/worker policies, full `@safe` scheduler promotion or any C++ speed claim. For the next bounded experiment, compare an unchanged uninstrumented M0 against **one** equivalent-semantics research variant, and first measure/calibrate central completion/ingress lock contention separately from failed steals and park/wake transitions. P14 remains research only; P06/P07 native join failure remains unresolved.
