## Narrow research question

P23 ensures an **ordinary** `Supervisor` holds a real
`OwnedTaskExecutor` *before* constructing the actual M0
`SubmissionWorkerPool`. It does not specify how that supervisor
remains reachable when every producer/controller handle disappears.

P24 tests a **process-reachable, bounded registry** over the same
source-pinned **P23** real-M0 executor. A module-lifetime named registry
retains the executor, and its `register()` also explicitly calls
`GC.addRoot(cast(void*) executor)` **before** any native worker starts.
The registry rejects root release while workers are active or native
shutdown is unproven; on `joinedStopped`, with all retained records
cleared, it calls `GC.removeRoot` exactly once and removes its own
strong reference.

This is a *deliberately redundant dual root* (module-lifetime registry
reference plus explicit druntime GC registration). It qualifies
correct and balanced root lifetime in this bounded design; it does
**not** prove that GC would reclaim the object if either root were absent,
because the D collector scans other roots conservatively.

### Runtime contract and evidence

The official [DMD 2.111.0 GC specification](https://docarchives.dlang.io/v2.111.0/spec/garbage.html)
lists `GC.addRoot` roots explicitly. The
[`core.memory.GC.addRoot` contract](https://dlang.org/library/core/memory/gc.add_root.html)
states that a registered GC block and the blocks reachable from it
remain live until its corresponding root is removed. That is the
intended transitive-GC reachability mechanism, **not** an implicit
ownership guarantee for arbitrary native pointers or caller-stack
borrows. `GC.addRange` is **not** an equivalent substitute: it adds
an externally managed region to scan without necessarily rooting the
region itself.

## Bounded registry responsibilities

The research `RootRegistry` has **two slots**, a Mutex protecting
bookkeeping, and explicit `added`/`removed` counters:

1. `register(executor)` requires `researchConstructed()` (no native
   worker launched), installs `GC.addRoot(executor)`, stores a strong
   executor reference and marks exactly one slot live. A full registry
   rejects further registrations, rather than silently evicting live
   owners.
2. `start(id)` invokes P23's explicitly deferred native-worker
   construction **only after** the separate root has been registered.
   Original `SubmissionWorkerPool` and D druntime launch remain real.
3. The task producer's `TaskHandle` and ordinary constructor/controller
   reference may both be dropped. The registry remains reachable via a
   separate process-lifetime module reference and can initiate shutdown
   subsequently. `borrow(id)` is a research-only short-lived view;
   no consumer-level arbitrary concurrent registry release contract is
   claimed.
4. `tryRelease(id)` checks for the P23 research executor's
   **verified-native-join** `isStopped()` and requires zero retained
   records. If not joined, it refuses to release; otherwise it makes
   exactly one matching `GC.removeRoot`, clears the registry slot and
   increments `removed`. A second release attempt is rejected.
5. A known *synthetic* pre-join exception may be followed by the **first
   actual native join** through P23's research-only recovery method.
   This method is never used to retry a native join that failed.

**Hard boundary:** the source-pinned P23 copy **aborts on actual
unqualified `Thread.start()` or native join failure**. P24 does not
add an OS-level failure-recovery path or justify freeing tasks after
such a failure. The process-rooted registry would otherwise need
a carefully specified permanent uncertainty/leak and shutdown policy.
D's native thread and GC lifetime details remain outside a blanket
`@trusted` claim; arbitrary `F` submission remains `@system`.

## P25 owner-mode comparison

[P25](../p25_owner_modes/README.md) compares this process-registry
ownership mode with a **noncopyable lexical LifetimeToken** under the
same source-pinned real M0 `OwnedTaskExecutor` and identical
accepted-task outcomes. The lexical token releases its registered
GC root only after actual joined shutdown and **fails the process**
if its scope exits without proved join; the registry permits the
controller scope to disappear while work is still owned. Compile
negative and separate `SIGABRT` gates distinguish the lifetime
contracts. Both modes have matched correctness evidence, **not**
measured performance equivalence or a general public `@safe` proof.

## Engineering disposition — conditional KEEP, production NO-GO

P24 supports a **registered-root ownership family** with an explicit
strong root installed before native launch and paired unregistration
only after actual native quiescence. It also supports independent
root obligations for concurrent, distinct executors.

This is **not evidence** that a module-global registry is the optimal
production design. An always-live registry incurs process-global state,
bounded-slot exhaustion policy, cleanup/leak responsibilities, shutdown
reentrancy/lock-order requirements, access-control and arbitrary
consumer-abandonment semantics. The controlled test only invokes
registry mutations from the control thread; it does not qualify
simultaneous registry register/release/find operations under adversarial
concurrency, fatal process teardown, druntime GC shutdown order, worker
self-join, or ownership of pointer-containing `F`. It is not a
cross-platform Windows/macOS native-exception proof.

**Next gate:** compare a process-wide managed root against a scoped
root registered through explicit executor lifetime tokens and
document the different availability costs. If a permanent registry is
proposed, demonstrate its synchronization and shutdown semantics and
bound its retention overhead before production promotion. Otherwise
specify the fatal policy explicitly; never infer native quiescence from
the fact that `closeAndJoin()` was invoked.

Keep ADR-0001 **PROPOSED**, Issue #17 **OPEN**, PR #38
**DRAFT**. No production merge and no changes to unrelated PR #35.
