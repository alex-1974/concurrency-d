# v0.3.0 release qualification

Status: **release candidate prepared; exact-candidate validation in progress**

This checklist tracks release gate [#27](https://github.com/alex-1974/concurrency-d/issues/27)
and M2 goal [#7](https://github.com/alex-1974/concurrency-d/issues/7). The
feature is being qualified on `develop`; version `0.3.0`, the signed tag and
publication are separate final steps after the exact candidate passes.

## Release requirements

- [x] Independent headless CPU and event-loop consumers compile and pass under
  DMD and LDC; event-loop state changes remain on the controller thread.
- [x] Consumer-controlled executor creation, bounded admission, cancellation,
  result observation and shutdown are documented and exercised.
- [x] DMD/LDC unit tests, public API/lifetime probes, lifecycle fault probes,
  and exported package consumers pass locally on the `0.3.0` release candidate.
- [x] Equivalent checksum-verified end-to-end adapters exist for Phobos,
  Taskflow, oneTBB and Rayon, including single-wave and reused-runtime modes.
  The local XPS evidence and its limits are recorded in the companion research
  repository at [signed report commit `fb32f4455b223206f017959d54c140aa1f0a8d7b`](https://github.com/alex-1974/concurrency-d-research/tree/fb32f4455b223206f017959d54c140aa1f0a8d7b/research/m2_cross_language_reference); the performance result is not a universal superiority claim.
- [x] Publish the signed feature commit and pass exact-commit GitHub CI on
  DMD, LDC, native ARM64 correctness and the cross-language reference smoke.
- [x] Capture and retain repeated native ARM64/LDC optimized performance data
  from the PR workflow; add its artifact and interpretation to the pinned
  research report.
- [ ] Make the v0.3.0 release-candidate commit, then rerun compiler, Ddoc,
  package-consumer, correctness and native ARM64 gates on that exact tree.
- [ ] Promote the exact candidate to `main`, verify the package archive and
  release metadata, create the signed `v0.3.0` tag and publish the GitHub
  release; verify the DUB registry entry.

## Performance interpretation

On one Dell XPS 15 capture, the best observed eight-wave `parallelFor` medians
were about 11–15% slower than Phobos for the selected four-worker workloads.
Rayon was close to or slightly faster than Phobos; Taskflow and oneTBB adapters
were slower in this specific harness. This is a measured limitation, not a
universal ranking. The library serves a different contract: an explicitly
owned executor with task lifetime, backpressure, typed results, cancellation,
shutdown and consumer-thread handoff. Keep those benefits separate from claims
about raw range-loop speed, and continue optimizing scheduling overhead and
tail behavior.

A native ARM64/LDC capture has completed on a four-core Neoverse-N2 runner with 28 paired samples per workload and tested grain. Reused fixed and adaptive range modes were near Phobos parity for medium, coarse and irregular work; the adaptive fine-work median was 23% lower at minimum grain 1, with a 12% higher p95. The full raw capture and methodology are documented in the [pinned companion report](https://github.com/alex-1974/concurrency-d-research/tree/fb32f4455b223206f017959d54c140aa1f0a8d7b/research/m2_end_to_end_qualification), with [workflow run #40484245846](https://github.com/alex-1974/concurrency-d/actions/runs/40484245846) and raw data.

The release can proceed only when the remaining unchecked items above have
exact-candidate evidence, including the versioned package consumer and main-targeted
CI.
