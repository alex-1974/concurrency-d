# v0.3.0 performance baseline for the next optimization

This baseline is captured from the exact `v0.3.0` tag, commit
`b4580d61cddadeeca3b99420a1aae2857b9de62e`. It is a diagnostic reference for
new performance work, not a release gate or a cross-machine guarantee.

Raw CSV, metadata, and complete benchmark summaries are retained in the
[research companion at pinned commit `af8bae2d0c32725c7d39a8e0bec6723a4be08b9c`](https://github.com/alex-1974/concurrency-d-research/tree/af8bae2d0c32725c7d39a8e0bec6723a4be08b9c/research/v0_3_release_baseline).
Both hosts ran the same release source, 4-worker/eight-wave end-to-end suite,
LDC release builds, 1,024 base iterations, four independent sessions, 20
measured pairs and five warmups per setting. Each arm validates an identical
checksum. Ratios below are paired elapsed-time ratios for the reusable
`parallelForAdaptive` arm divided by the matching reused Phobos arm. The
reported grain is selected by pooled p50 for each workload; it is not a
portable tuning recommendation.

## What this supports

The adaptive range path is effectively at Phobos median parity on the XPS for
these selected settings. Its pooled fine-work p95 is elevated, but the four
session p95 ratios at minimum grain 1 are 1.055, 1.227, 1.129 and 1.043. The
tail is therefore sensitive to session-level variation. On ARM64, the fine
workload is consistently about 3% slower than Phobos at its selected minimum
grain; the other workloads are at parity. The best fine-work minimum grain
differs sharply between the two hosts.

This evidence does not identify the cause or justify a high-risk scheduler
redesign. It also does not support a universal target such as “beat Phobos.”
Treat the XPS p95 as a profiling clue, not an established cross-platform
regression.

## Next diagnostic and acceptance

Profile the fine adaptive path first and separate range-claim cost, scope/task
dispatch, callback work, and join/drain time. Do not change parking or task
record storage unless the profile identifies either as material; [ADR-0003](adr/0003-coalesce-idle-publish-notifications.md)
and [ADR-0005](adr/0005-keep-gc-owned-task-records.md) retain the simplest
qualified choices.

Before implementing a candidate, predeclare one primary metric and a practical
minimum improvement larger than the observed run-to-run noise. Re-run the same
four-session paired protocol on XPS and native ARM64, compare directly against
this exact-tag baseline, and report each session as well as pooled p50/p95/p99.
Require DMD/LDC correctness, exact-once range coverage, error-drain and
executor-reuse checks, and no material regression in medium, coarse,
irregular, or single-worker controls. Assign a v0.4.0 release target only if a
candidate clears those checks; otherwise retain the baseline without adding a
speculative API or scheduler policy.

For the fine-range scheduler investigation, predeclare the primary endpoint as
the paired `parallelForAdaptive` elapsed-time ratio for the 16-step short
uniform callback at four workers and minimum grain 1, candidate over exact
`v0.3.0` baseline. Require at least a 15% pooled median improvement (ratio at
most 0.85), with the direction of benefit present in every session. The
diagnostic's adaptive/fixed session medians currently span 0.714–0.792, a
7.8-percentage-point spread; the 15% threshold is deliberately larger than
that observed session variation. Treat p95/p99 and all medium, coarse,
irregular, and single-worker cases as guardrails: investigate any repeatable
regression above 10%, and do not accept a candidate whose tail behavior
materially worsens. This predeclares a gate; it does not imply that an
optimization candidate exists or that the current scheduler meets it.

The subsequent four-session grain screen found that minimum grain 64 clears
the short-uniform median threshold on both tested hosts, but fails the tail
guardrails: p95 regresses by 38% on the XPS heavy-suffix workload and 12% on
ARM64, with further p95 regressions on long uniform work. Therefore grain 64
is not selected as a default or scheduler change. The protocol, raw captures,
and per-session summaries are in the [grain-screen results](https://github.com/alex-1974/concurrency-d-research/tree/98cacfa/research/m3_fine_adaptive_profile/results/grain_screen).
